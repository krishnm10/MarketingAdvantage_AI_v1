This report reviews the rustPython branch of
krishnm10/MarketingAdvantage_AI_v1, focusing on ingestion,
deduplication, retrieval, and configuration pipelines, and proposes
changes needed to reach a world‑class, production‑ready RAG
platform.
The analysis covers concrete defects (crash risks, data‑loss paths,
stale config behavior), architectural gaps (hard‑wired chunking, static
UI), and process/quality recommendations to support long‑term
maintainability and multi‑tenant safety.
IngestedFileV2.business_id is a PostgreSQL UUID(as_uuid=True), so
ORM instances expose a uuid.UUID object at runtime.
The _get_pipeline helper takes an optional business_id parameter but
immediately calls (business_id or "default").lower().replace("-", "_"),
which will raise AttributeError when business_id is a uuid.UUID
rather than a string.
_run_pipeline passes file_record.business_id directly into
_get_pipeline, so any file with a non‑null tenant can crash ingestion
during pipeline resolution.

2. High‑Severity Technical Issues
2.1 Business ID handling and pipeline resolution


--- PAGE 2 ---
Normalize tenant IDs to strings at the API boundary of
_get_pipeline, for example: raw = str(business_id) if business_id
is not None else "default"; b = raw.lower().replace("-", "_").
Document the expected type for business_id (stringified UUID)
and avoid passing ORM objects directly from models into
env‑key munging helpers.
Add tests that ingest files for multiple tenants with true UUIDs
and assert successful pipeline resolution per tenant.
_get_pipeline is decorated with @lru_cache(maxsize=16) and reads its
configuration purely from environment variables, constructing a
ClientConfig and then calling pipeline_factory.build(config).
The config API invalidates pipeline_factory’s internal cache and
updates .env/os.environ, but it never clears the _get_pipeline LRU
cache, so previously‑built pipelines for a given business_id continue
to be returned unchanged even after config updates.
This produces confusing "stale config" behavior where admin
changes appear to succeed but are not reflected in live requests until
the process restarts or the cache is otherwise evicted.
Recommendations
Expose a small invalidation API on the ingestion side, e.g.,
_get_pipeline.cache_clear() and call it from the config update
handler whenever vector DB, embedder, or LLM config is
changed.
Consider moving caching responsibility fully into
pipeline_factory and making _get_pipeline a thin, uncached
resolver over pipeline_factory.get_or_build, so there is a single
cache to invalidate.
Add an integration test that performs a config update (e.g.,
change embedder type), hits the RAG API twice, and asserts that
the second call uses the new backend without restart.
2.2 LRU‑cached pipelines and stale configuration


--- PAGE 3 ---
The retrieval policy registry holds singleton RetrievalPolicy instances
keyed by intent, and DEFAULT_POLICY_REGISTRY.resolve() returns
the same object for all requests of that intent.
The retrieval API then mutates shared state by setting
policy.max_results = req.top_k inside the request handler, causing
per‑request top_k values to leak into the global policy and affect
subsequent, unrelated requests.
In a multi‑tenant or multi‑user deployment, this leads to
non‑deterministic behavior where one user’s requested top_k silently
changes the default for others.
Recommendations
Treat top_k (or max_results) as a per‑request parameter passed
into repository / runtime methods instead of mutating policy
objects, or clone the policy template per request and adjust the
clone only.
Ensure DEFAULT_POLICY_REGISTRY.resolve() returns either an
immutable spec or a fresh RetrievalPolicy instance each time,
not a shared mutable object.
Add concurrency tests (or at least multi‑request tests) to assert
that parallel calls with different top_k values do not affect each
other.
The 3‑layer dedup engine’s L3 stage runs vector‑similarity checks
concurrently and collects results using asyncio.gather(...,
return_exceptions=True), but in the branch where a batch result is an
exception, the code logs a warning and increments stats["unique"]
while not appending the corresponding chunk to unique_chunks or
any other output list.
Because _run_pipeline writes dedup stats from stats but later uses
unique_chunks to drive GCI registration, storage, and embedding,
these L3‑errored chunks are effectively dropped while still counted as
unique, reducing recall and corrupting metrics.
Recommendations

In the L3 exception branch, explicitly append the original
chunk(s) to unique_chunks so they continue through GCI
registration, storage, and embedding despite the L3 failure.
Alternatively, maintain a separate errored_chunks bucket but
still pass them through to storage and embedding, marking them
with diagnostic metadata in reasoning_ingestion.
Extend tests around deduplicate_chunks to simulate L3
exceptions and assert that no original chunks are lost.
RAGResult.summary() tries to format the trust score inline as f"trust=
{self.trust_score:.2f if self.trust_score else 'N/A'} | ...", but in Python
the format specifier cannot contain conditional logic, so this code
always raises ValueError when formatting, regardless of whether
trust_score is None or a float.
Because query() unconditionally calls logger.info("[RAGPipeline] %s",
result.summary()) on success, every successful pipeline execution is
followed by a logging‑time exception originating from the summary
method.
Recommendations
Refactor summary formatting to compute trust_str separately,
for example: trust_str = f"{self.trust_score:.2f}" if self.trust_score
is not None else "N/A"; ... f"trust={trust_str} | ...".
Add a small unit test for RAGResult.summary() that covers
trust_score=None and a numeric value to guard against future
regressions.
The ingestion service itself uses a strict media‑level hash dedup check,
computing incoming_hash from the file path and comparing only
meta_data["file_hash"] for already‑processed files before
hard‑stopping duplicates, which is safe.
However, there are indications in the router layer that file‑name
based skipping may be applied (file_name == original_file_name),
which risks false positives when different files share names (for
example, refreshed exports from business systems).

Recommendations
Constrain all skip decisions to strong identifiers (media_hash /
file_hash and GCI‑backed semantic hashes) and remove any
OR‑branch that treats bare file_name equality as sufficient for
deduplication.
Record any name‑based soft signals in metadata only (e.g., for
UX), not as hard dedup gates.
_dedup_chunks treats a batch as structured data when source_type of
the first chunk is one of "csv", "xlsx", or "xls", in which case L3 vector
similarity dedup is disabled in favor of L1/L2 only.
The Excel parser, however, sets source_type="excel" when building
row‑level chunks through parse_dataframe_rows, so these rows
incorrectly fall through to L3 dedup, incurring unnecessary
embedding and similarity checks for row‑based content where L1/L2
are sufficient.
Recommendations
Normalize source_type for Excel inputs to match the file
extension ("xlsx" or "xls") so the existing structured‑data bypass
applies.
Alternatively, expand the structured‑data detection condition to
include "excel" to be robust against legacy values.
The RAG API’s auto‑config path checks for client configs under a
top‑level configs/{client_id}.json or .yaml, but the repository tree for
this branch only contains app/core/configs/, so the default search
path will not find these files unless a separate configs/ directory is
created in the deployment environment.
The route then reads pipeline_factory._cache directly to retrieve the
pipeline, coupling API behavior to a private cache implementation
detail rather than a stable public API.

Make the config search path configurable and default it to

The repository’s normalization function currently iterates snapshots
in list order, returning the first dict that contains a tap_trust_score
key, and if none have it, the first valid snapshot overall.
Although helper functions exist to derive timestamps from snapshots,
_normalize_signal does not use them, so the “winning” snapshot is
purely position‑based, which may not align with an expectation of
“latest by time” in downstream consumers or tests.
Recommendations
Decide explicitly whether normalization semantics should be
“first with agentic trust score” or “latest by timestamp with
agentic trust score” and reflect that choice in both code and tests.
If “latest” is desired, sort or reduce snapshots by parsed
timestamp before applying the trust‑score selection logic, and
use _extract_timestamp consistently.
The ingestion pipeline invokes recursive_semantic_chunk directly in
multiple paths (single‑payload text, multi‑item text, visual
explanations) without any indirection or strategy selection.
At the same time, ClientConfig and IngestionConfig define
ChunkConfig and ChunkStrategy, but runtime ingestion logic does not
read or honor these fields, so there is no way to switch chunking
behavior per client or per pipeline despite the schema support.

4. Architecture and Performance
Recommendations
4.1 Use PluginRegistry for chunkers and RAG
components


--- PAGE 9 ---
_get_pipeline so ingestion can call pipeline.chunker.chunk(...)
instead of recursive_semantic_chunk directly.
The current pipeline resolver already supports per‑tenant
configuration via per‑business env overrides such as
MAI_{BUSINESS_ID}_VECTORDB and uses client_id in ClientConfig.
However, the chunking and dedup configurations are still effectively
global or implicit, and config updates do not reliably propagate due to
the LRU caching issue.
Recommendations
Treat each tenant’s pipeline as an explicit object with its own
vector DB, embedder, LLM, chunker, and dedup configuration,
resolved via a uniform mechanism (env, file, or DB row) rather
than scattered .env keys.
Make these configurations observable (via admin APIs) and
editable via a central config UI instead of relying solely on env
files.
ingestion_service_v2 contains complex coordination code around
SQLAlchemy async sessions, multi‑layer dedup, and GCI writes, but
the computational hotspots are around chunking, token counting,
and vector hashing.
Moving these hotspots into Rust via a pyo3/maturin module, while
keeping orchestration, I/O, and pluggability in Python, aligns with the
existing architecture and avoids rewriting business logic.
Recommendations
Define a narrow FFI surface in Rust that exposes chunking and
tokenization as pure functions, parameterized by strategy and
limits, without any direct DB or network access.
Call this Rust module from within registered chunker plugins so
the ingestion service only sees a uniform chunk() API while
implementation details (Rust vs Python) remain encapsulated.
4.2 Per‑tenant and per‑pipeline configurability
4.3 Python orchestration + Rust for heavy compute


--- PAGE 10 ---
Use Rust crates like unicode-segmentation, regex, and tiktoken-
rs for robust multilingual splitting and model‑aligned token
counting, and use rayon for intra‑file parallelism in larger
documents.
Given the number of moving parts (vector DB backends, remote vs
local embeddings, network latency), strict "2× faster or fail"
thresholds in CI would lead to flaky builds and noise, not meaningful
performance assurance.
A trend‑based approach, where benchmark results are recorded and
compared over time, gives better insight into regressions and
improvements across releases.
Recommendations
Create a small benchmark suite that ingests representative PDFs,
CSV/Excel files, and multi‑page web/RSS payloads through the
full pipeline (parsing → chunking → dedup → embedding →
upsert) with instrumentation.
Run these benchmarks in CI under controlled conditions (e.g., a
known local vector DB and embedder backend) and track
medians and p95 latencies across commits, alerting on
significant regressions instead of imposing fixed absolute
thresholds.
The current codebase already includes focused tests in some areas
(such as signal normalization) but leaves critical paths like chunking
strategy selection and multi‑layer dedup under‑tested.
World‑class quality will require systematic coverage of ingestion
workflows, dedup correctness, retrieval behavior, and configuration
propagation.

5.1 Testing and quality gates


--- PAGE 11 ---
Add scenario tests that start from file upload (PDF, DOCX,
CSV/Excel, web/RSS) and assert end‑to‑end outcomes: DB rows
inserted, GCI entries, dedup stats consistency, and vector DB
contents.
Add property‑style tests for chunking invariants (no empty
chunks, consistent overlap, idempotent segmentation for a given
strategy) and dedup invariants (no false positives in L1/L2 for
non‑identical content, L3 recall properties).
Make regression tests for each fixed high‑severity bug so they
can never regress silently.
The ingestion service already logs detailed messages about hash
dedup, structured vs text paths, and vector DB operations, but these
logs are not yet surfaced in any aggregated observability layer.
A world‑class product should make it easy to answer “what
happened to this file?” or “why did this query return these
documents?” in a few clicks.
Recommendations
Persist ingestion events (file status transitions, dedup layer
counts, GCI registration) and retrieval traces (selected chunks,
scores, policies) in a structured log or tracing system.
Build admin views that surface per‑file pipelines (parse → chunk
→ dedup → embed → upsert) and per‑query retrieval diagnostics
(policy used, vector DB backend, reranker decisions).
With per‑business configuration, UUID tenant IDs, and pluggable
backends, the system is well‑positioned for multi‑tenant
deployments, but issues like singleton policy mutation and cached
pipelines can undermine isolation.
World‑class readiness demands clear boundaries between tenants at
both configuration and runtime state levels.
Recommendations

5.3 Multi‑tenant safety and isolation


--- PAGE 12 ---
Ensure all cached state (pipelines, policies, chunkers) is keyed by
tenant and that no mutable singleton state is shared across
tenants.
Add automated tests that simulate two tenants with different
configs and assert that changes and requests for one do not
affect the other.
The introduction of a 3‑layer dedup pipeline (hash, GCI, embedding)
and a GlobalContentIndex shows a strong focus on data quality and
cross‑file deduplication.
To reach world‑class robustness, the error paths (such as L3
exceptions and compensation cleanup) must be as carefully specified
as the happy paths.
Recommendations
Treat every potential data‑loss path (like the L3 exception case)
as a P0 until proven otherwise, with explicit design decisions
about fail‑open vs fail‑closed behavior and tests to back them.
Add background integrity checks that periodically validate
invariants between ingested_file, ingested_content,
GlobalContentIndexV2, and vector DB contents, reporting
anomalies for operator action.
The current admin UI for pipelines is more of a static diagram than a
live control plane, and there is no unified view of per‑tenant
configuration and health.
For a world‑class SaaS‑like RAG platform, strong admin UX is
essential for adoption and trust.
Recommendations
Build a “Tenant Overview” dashboard showing, per business:
active pipeline components (vector DB, embedder, LLM,
chunker), last ingestion activity, error rates, and storage
footprints.
